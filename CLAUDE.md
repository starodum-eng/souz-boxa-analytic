# Союз Бокса — сквозная аналитика

Дашборд сквозной аналитики для клуба единоборств «Союз Бокса». Собирает данные из
рекламы, веб-аналитики, коллтрекинга и CRM в единую воронку:

**Реклама (расход) → Визиты → Лиды → Клиенты → Выручка → ROMI**, с атрибуцией по каналам.

## Стек и инфраструктура

- **Next.js 15** (App Router, TypeScript, React 19) на **Vercel** (план Hobby).
- **Neon** (serverless Postgres) + **Drizzle ORM** (`@neondatabase/serverless`, драйвер `neon-http`).
- **Recharts** для графиков. Никаких тяжёлых зависимостей — CSV парсим сами.
- Пакетный менеджер — **pnpm** (не npm! у npm ломается lockfile).
- Рабочая ветка разработки: `claude/confident-fermi-h5sy81`. Vercel деплоит именно эту ветку
  (отдельной `main` в репо нет — эта ветка и есть production).

### Ограничения Vercel Hobby (важно!)
- Крон только **раз в сутки** — `vercel.json`: `/api/cron/sync` в `0 6 * * *`.
- Таймаут функции ~60 сек (`maxDuration=300` НЕ работает на Hobby). Синк должен укладываться —
  поэтому вставки в БД **пакетные** (chunk 500), а не построчные.

### Миграции БД
Sandbox/агент **не имеет сетевого доступа к Neon** (и к Яндексу/Fitbase/Callibri). Поэтому:
- `pnpm db:generate` создаёт SQL-миграцию в `drizzle/`.
- Пользователь **вручную** выполняет её в Neon SQL Editor. Всегда давай ему готовый SQL.

## Ключевые файлы

- `src/lib/etl.ts` — оркестратор `runFullSync()`: тянет все источники, пакетно пишет в БД,
  в конце `recomputeDailyMetrics()` (витрина). Fitbase-эндпоинты грузятся ПОСЛЕДОВАТЕЛЬНО
  (внутри — параллельная пагинация, см. ниже).
- `src/app/api/metrics/route.ts` — главный запрос дашборда (`?from&to`). Считает: totals,
  bySource (расход+лиды+клиенты+касса+ROMI когорты по каналам), lifetimeByChannel (LTV за всё время),
  channelInfluence (мультитач), byDate (сводка по дням), timeline, lastSync.
- `src/app/api/import-sales/route.ts` + `src/lib/csv.ts` — импорт выручки из CSV (см. ниже).
- `src/app/api/retention/route.ts` — данные удержания (кому звонить / не ходят / структура продаж).
- `src/app/api/sync-now/route.ts` — кнопка «Обновить данные» (POST → runFullSync).
- `src/components/App.tsx` — вкладки: **Дашборд · Источники · Удержание · Импорт · Справка**.
  Маршруты `/import`, `/retention` открывают соответствующую вкладку.
- `src/middleware.ts` — Basic Auth на дашборд.
- `src/db/schema.ts` — все таблицы.

## Главное решение проекта: ВЫРУЧКА берётся из импорта, а не из API

**Объектный API Fitbase (`/client-contract`, `/client-service`, `/client-product`) НЕ отдаёт
онлайн-платежи и продления (CloudPayments).** Из-за этого касса недосчитывалась в ~2.3 раза
(66 400 против 152 440 за период). Проверено: продления не приходят ни новой строкой контракта,
ни обновлением `payment_date`; в детали контракта их тоже нет; отдельного платёжного эндпоинта в
API v2 не существует.

**Источник правды по выручке — отчёт Fitbase «Отчёты → Финансы → Отчёт по продажам»**, выгружается
в CSV и заливается на вкладке **Импорт** (`/import`) → таблица `sales_ledger`. Там есть ID клиента
(для атрибуции по каналам), способ оплаты, тип, «Оплачено, ₽» (= сумма выручки). Сумма импорта
сходится с Fitbase точь-в-точь.

- CSV: разделитель `;`, UTF-8 BOM, поля в кавычках. Колонки маппятся **по заголовкам** (не по
  позиции). Сумма = колонка **«Оплачено, ₽»**.
- **Дедуп по `ext_id`** = хэш(чек + клиент + дата + сумма + наименование + тип). ВАЖНО: один чек
  может покрывать несколько позиций (абонемент + товар одной оплатой) — поэтому ключом НЕ может быть
  только номер чека (иначе теряются позиции и недосчитывается касса). Повторная загрузка не плодит дубли.
- Первый импорт делают **за длинный период** (напр. 01.01.2025 — сегодня), чтобы LTV/ROMI были полными.

## Метрики: смысл (см. вкладку «Справка»)

- **Касса за период** — реальные оплаты из `sales_ledger` по `pay_date` в окне. Сходится с Fitbase.
  Итог берётся как ПОЛНАЯ сумма журнала за период (включая строки без ID клиента → канал «Не определён»).
- **Средний LTV клиента** — вся выручка ÷ число платящих клиентов (за всё время).
- **LTV по каналам за всё время** — отдельная таблица `lifetimeByChannel`: какой канал приводит
  самых денежных клиентов (не зависит от периода).
- **ROMI когорты** — единственный ROMI на дашборде: `(LTV привлечённых за период клиентов − Расход) ÷ Расход`.
  Честная окупаемость рекламы. «ROMI (касса)» и «LTV когорты за период» УБРАНЫ по просьбе владельца
  (касса-ROMI завышен продлениями старых клиентов; когортный LTV за короткий период «не дозрел»).
- **Атрибуция**: канал клиента = ПЕРВОЕ касание (lead_touches по телефону + fitbase_leads по UTM/advertising_source).
  Витрина `daily_metrics` классифицирует канал: source_mappings.label > utm yandex/vk > traffic_source
  (yandex_business/organic/direct) > «Сайт (прочее)». Ярлык источника `null` → «Не определён».

## Таблицы (schema.ts)

- `ad_spend` — расход Директ/VK по дням.
- `web_sessions` — визиты/цели Метрики (utm-пустые хранятся как `''`, не NULL, для дедупа).
- `clients` — клиенты Fitbase.
- `fitbase_leads` — лиды воронки Fitbase (UTM, advertising_source, client_id).
- `client_contracts` — абонементы (используются для удержания: `end_date`).
- `client_payments` — старый «единый кассовый» слой (контракты+услуги+товары из API). **Больше НЕ
  источник выручки** (недосчитывал). Оставлен на всякий случай; метрики читают `sales_ledger`.
- **`sales_ledger`** — журнал продаж из CSV-импорта. **Источник правды по выручке/LTV.**
- `client_visits` — визиты (для удержания «не ходят»).
- `daily_metrics` — витрина день × канал (пересобирается в `recomputeDailyMetrics`).
- `lead_touches` — касания из Callibri/форм (мост «телефон ↔ источник»).
- `source_mappings` — справочник UTM → человекочитаемый канал (вкладка «Источники»).
- `sync_log` — статусы синхронизаций.

## Аутентификация (важный нюанс!)

`src/middleware.ts` — Basic Auth (`DASHBOARD_USER`/`DASHBOARD_PASSWORD`). Если ENV не заданы —
не блокирует (чтобы не залочиться).

**НЕ гейтить статику и вебхуки**, иначе внешний сайт, подключающий `/lead-tracker.js`, ловит попап
авторизации браузера. Публичны: любые файлы с расширением (`STATIC_FILE` regex, вкл. `lead-tracker.js`),
`/api/lead` (заявки с сайта), `/api/cron` (крон с Bearer CRON_SECRET). Всё остальное — под логином.

## Особенности Fitbase API (fitbase.ts)

- Заголовки: `Authorization: Bearer <FITBASE_API_KEY>` + `domain: <FITBASE_DOMAIN>`.
- `page_size` максимум 100. Пагинация: **грузим до первой неполной страницы**, НЕ доверяя
  `total_count` (Fitbase отдаёт его с запаздыванием — иначе теряются самые свежие записи).
- Пагинация небольшими параллельными пачками (CONCURRENCY=3) + повтор при **429** (лимит частоты).
- Даты: часть полей — unix-секунды, часть — ISO-строки (напр. `begin_date` = «2024-02-15»).

## Развёртывание / рабочий цикл

1. Правки → коммит → `git push -u origin claude/confident-fermi-h5sy81` (Vercel авто-деплоит).
2. Если менялась схема — дать пользователю SQL из `drizzle/*.sql` для ручного прогона в Neon.
3. Проверять `pnpm typecheck` (`node_modules/.bin/tsc --noEmit`) перед пушем.
4. ENV меняются только через новый деплой (Redeploy).
